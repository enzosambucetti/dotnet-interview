Patrón arquitectónico: sincronización event-driven con una tabla durable de SyncEvents y jobs de Hangfire. No es Event Sourcing: el estado actual vive en TodoLists y Items, y los eventos se usan para integración, auditoría, retries y recovery. Tampoco es un Transactional Outbox estricto: la mutación local y el SyncEvent se persisten antes del enqueue, pero el enqueue de Hangfire ocurre después y se mitiga con un recovery job. El flujo inbound usa Polling periódico con reconciliación completa.

3. Flujo Outbound – Local → API Externa

Outbound Se dispara sincrónicamente en cada mutación local (Create/Update/Delete). El Service persiste la entidad, luego crea un SyncEvent durable, y después encola un job de Hangfire. El enqueue no forma parte de la misma transacción exacta, por eso existe el recovery job.

sequenceDiagram
    actor U as Usuario
    participant CTRL as Controller
    participant SVC as Service
    participant DB as SQL Server
    participant PUB as SyncEventPublisher
    participant HF as Hangfire
    participant OUT as OutboundSyncJob
    participant EXT as ExternalApi

    U->>CTRL: POST /api/todolists {name: "Work"}
    CTRL->>SVC: CreateTodoListAsync(payload)
    SVC->>DB: INSERT TodoList
    Note over SVC,DB: SaveChangesAsync de la entidad
    SVC->>PUB: PublishAsync("TodoList", id, "Created", entity)
    PUB->>DB: INSERT SyncEvent (Status=Pending)
    Note over PUB,DB: SaveChangesAsync separado para SyncEvent
    PUB->>HF: BackgroundJob.Enqueue<IOutboundSyncJob>(syncEventId)
    SVC-->>CTRL: TodoList creado
    CTRL-->>U: 201 Created

    Note over HF,OUT: Hangfire ejecuta el job en background

    HF->>OUT: ProcessAsync(syncEventId)
    OUT->>DB: SELECT SyncEvent WHERE Id=syncEventId
    OUT->>DB: Verificar si es obsoleto (entidad soft-deleted?)
    OUT->>DB: UPDATE Status=Processing, Attempts++

    alt EntityType=TodoList, EventType=Created
        OUT->>DB: SELECT TodoList + Items
        OUT->>EXT: POST /todolists {source_id, name, items[]}
        EXT-->>OUT: 201 {id: "ext-list-003", items[{id: "ext-item-004"}]}
        OUT->>DB: UPDATE TodoList.ExternalId = "ext-list-003"
        OUT->>DB: UPDATE Items[].ExternalId = "ext-item-004"
    else EntityType=TodoList, EventType=Updated
        OUT->>DB: SELECT TodoList (verificar ExternalId != null)
        OUT->>EXT: PATCH /todolists/{externalId} {name}
    else EntityType=TodoList, EventType=Deleted
        OUT->>DB: SELECT TodoList (verificar ExternalId != null)
        OUT->>EXT: DELETE /todolists/{externalId}
    end

    OUT->>DB: UPDATE SyncEvent Status=Completed, ProcessedAt=UtcNow

Dependencia de creación padre→hijo

Un Item no puede sincronizarse outbound hasta que su TodoList padre tenga ExternalId. Si el create del padre aún está pendiente, el OutboundSyncJob lanza SyncDependencyPendingException, regresa el evento a Pending, y decrementa Attempts para no penalizar la espera legítima.

4.1 Estrategia de Búsqueda (Deduplicación Inbound)

La búsqueda de entidades locales usa una cascada de 3 criterios para evitar duplicados:

  1. Por ExternalId – Match directo con external.Id.
  2. Por SourceId – Si no se encuentra por ExternalId y el external tiene source_id.
  3. Por Id local – Si source_id es un long parseable, se intenta como PK local.

Se usa IgnoreQueryFilters() en todas las búsquedas para incluir entidades soft-deleted y evitar re-creaciones.

Si el match encuentra una entidad local soft-deleted, inbound la restaura solo cuando DeletedAt < external.created_at. Si DeletedAt >= external.created_at, se mantiene el soft-delete y no se importan hijos debajo de esa lista, porque puede ser la ventana normal entre un delete local y el outbound delete.

5. Recovery Job – Recuperación de Eventos Fallidos

Recovery El SyncEventRecoveryJob también corre cada 1 minuto via RecurringJob. Busca eventos estancados y los re-encola.

sequenceDiagram
    participant HF as Hangfire (Cron.Minutely)
    participant REC as SyncEventRecoveryJob
    participant DB as SQL Server

    HF->>REC: ProcessAsync()
    REC->>DB: SELECT TOP 50 SyncEvents
WHERE Status IN ('Pending','FailedRetryable','Failed')
AND Attempts < 5
ORDER BY CreatedAt ASC
    DB-->>REC: [{id:1}, {id:5}, {id:12}]

    loop Para cada SyncEvent recuperable
        REC->>HF: BackgroundJob.Enqueue<IOutboundSyncJob>(syncEvent.Id)
    end

    Note over REC: Los jobs se ejecutarán según la
capacidad del Hangfire Server

Criterios de recuperación:

  • Status = Pending – Eventos que nunca se procesaron o que quedaron en espera por dependencias.
  • Status = FailedRetryable – Fallos transitorios (5xx, timeout, network).
  • Status = Failed – Fallos genéricos que aún no agotaron intentos.
  • Attempts < 5 – Máximo 5 intentos totales.

7. Estrategia de Reintentos

7.1 Reintentos a nivel de HTTP Client

ExternalTodoApiClient.SendAsync implementa un retry loop interno:

  • Máximo: ExternalApiOptions.MaxRetries (default: 3).
  • Backoff: Lineal – 200ms × attempt (200ms, 400ms, 600ms).
  • Excluye 404: Los NotFound no se reintentan a nivel HTTP (se propagan al job).
  • Scope: Esto es por cada invocación individual del client, no del job.

Errores clasificados como retryable

  • HttpStatusCode.RequestTimeout (408)
  • HttpStatusCode.TooManyRequests (429)
  • Cualquier status >= 500 (Server errors)
  • TaskCanceledException, TimeoutException, HttpRequestException

Errores clasificados como terminales

  • Entidad local no encontrada en DB.
  • Entidad sin ExternalId y sin create pendiente.
  • Cualquier SyncTerminalException explícita.

8. Idempotencia y Deduplicación

8.1 Outbound – Idempotencia

  • Guard de status final: Si el SyncEvent.Status es Completed o FailedTerminal, el job retorna inmediatamente (IsFinalStatus).
  • Guard de obsolescencia: Si la entidad fue soft-deleted entre la creación del evento y su procesamiento, TryCompleteObsoleteEventAsync marca el evento como Completed sin hacer la llamada HTTP.
  • Guard de ExternalId ya existente: Para Created, si ExternalId ya tiene valor (otro job o inbound lo asignó), el create se omite.
  • Reconciliación post-error: Si un create falla ambiguamente (timeout, 5xx, conflict), se ejecuta un inbound sync para verificar si el recurso se creó. Si ExternalId quedó asignado, se marca como Completed.

9. Casos de Borde

9.1 Job falla a mitad del proceso

Escenario: El POST a ExternalApi fue exitoso pero el UPDATE local falla

Si ProcessTodoListCreatedAsync logra crear el recurso externo pero falla al guardar el ExternalId localmente:

  1. El SyncEvent queda en FailedRetryable.
  2. El SyncEventRecoveryJob lo re-encola.
  3. En el siguiente intento, el create outbound verifica ExternalId. Como es null, puede intentar crear de nuevo.
  4. Si la API externa rechaza con 409 Conflict, falla con timeout/5xx, o inbound encuentra el recurso por source_id, se activa la reconciliación.
  5. Se ejecuta un InboundSync que trae el snapshot externo y asigna el ExternalId correctamente.
  6. El evento se marca como Completed.

Limitación: si el proveedor externo permite duplicados con el mismo source_id y no devuelve un error reconciliable, un retry podría crear duplicados. Para producción, antes de repetir un create sin ExternalId convendría ejecutar una reconciliación preventiva.

9.2 Conflicto de versiones entre APIs

Estrategia: Last-Write-Wins basado en UpdatedAt

Durante el inbound sync, si una entidad existe localmente y la versión externa tiene cambios:

  • Si local.UpdatedAt > external.UpdatedAt → Local gana. Se logea un warning pero no se aplica el cambio externo.
  • Si local.UpdatedAt <= external.UpdatedAt → Externo gana. Se actualiza la entidad local.

El outbound no tiene resolución de conflictos explícita: siempre envía el estado local actual. Si la API externa rechaza (4xx), se clasifica el error según su tipo.

9.3 Entidad eliminada externamente (404 en outbound)

Si un outbound update/create recibe 404 Not Found:

  1. Se ejecuta un InboundSync completo como reconciliación.
  2. Si tras la reconciliación la entidad local quedó soft-deleted → Completed.
  3. Si no se resolvió → FailedRetryable.

Excepción: Si el evento es un Delete y recibe 404, se marca Completed directamente (el recurso ya no existe, que es el resultado deseado).

9.4 Race condition: Outbound y Inbound simultáneos

Dado que el OutboundSyncJob puede disparar un InboundSyncJob inline (reconciliación), y el InboundSyncJob corre como RecurringJob, existe la posibilidad de ejecución concurrente. Mitigaciones:

  • La mitigación principal es la idempotencia del flujo, la búsqueda por ExternalId/SourceId y la comparación por UpdatedAt. No hay control optimista fuerte con rowversion, por lo que conflictos concurrentes reales no se detectan automáticamente a nivel EF.
  • El inbound es idempotente: upsert basado en la cascada de búsqueda. Procesar dos veces el mismo snapshot externo no genera duplicados.
  • El outbound verifica ExternalId antes de crear: si el inbound ya lo asignó, el create se omite.

10. Máquina de Estados de SyncEvent

Pending → Processing → Completed
Processing → FailedRetryable → Re-enqueue → Processing
Processing → FailedTerminal (fin)
