Flujo SignalR Realtime – TodoApi

Cómo TodoApi notifica cambios en tiempo real a los clientes conectados via SignalR, tanto desde mutaciones locales como desde el inbound sync.

Hub: TodoUpdatesHub es un Hub vacío (sin métodos server-side). Solo se usa como canal de broadcast vía IHubContext. El endpoint es /hubs/todo-updates.

Evento único: Todos los mensajes se envían al client method "todoUpdated" con un payload tipado TodoRealtimeEvent.

Broadcast: Se envía a Clients.All — todos los clientes conectados reciben todos los eventos.

2. Flujo desde Mutación Local (API REST)

Source: LocalApi Cada Create / Update / Delete en los Services emite un evento SignalR inmediatamente después de persistir.

    U->>CTRL: POST /api/todolists {name: "Work"}

    NTF->>HUB: SendAsync("todoUpdated", event)

3. Flujo desde Inbound Sync (Hangfire → SignalR)

Source: InboundSync El InboundSyncJob acumula eventos durante toda la reconciliación y los emite en batch al final.

sequenceDiagram
    participant HF as Hangfire (cada 1 min)
    participant INB as InboundSyncJob
    participant EXT as ExternalApi
    participant DB as SQL Server
    participant NTF as SignalRTodoRealtimeNotifier
    participant C as Clientes WebSocket

    HF->>INB: ProcessAsync()
    INB->>EXT: GET /todolists
    EXT-->>INB: [{id, name, items[]}, ...]

    Note over INB: Procesar cada lista e item

    loop Upsert TodoLists + Items
        INB->>DB: INSERT / UPDATE entidades
        Note over INB: Acumular en List<TodoRealtimeEvent>
    end

    loop Soft-delete faltantes
        INB->>DB: UPDATE IsDeleted = true
        Note over INB: Acumular TodoListDeleted / ItemDeleted
    end

    INB->>DB: SaveChangesAsync()

    Note over INB,NTF: Agregar evento resumen
    Note right of INB: EventType: InboundSyncCompleted
Source: InboundSync
Payload: {changed: N}

    INB->>NTF: PublishManyAsync(allEvents)

    loop Para cada evento acumulado
        NTF->>C: SendAsync("todoUpdated", event)
    end

    Note over C: El cliente recibe N+1 eventos:
N cambios individuales +
1 InboundSyncCompleted

Patrón Batch: A diferencia del flujo local (que emite 1 evento por operación), el inbound acumula todos los eventos en una lista durante el procesamiento y los envía todos juntos al final con PublishManyAsync. Esto asegura que los eventos solo se emiten si la transacción de DB fue exitosa.

Diferenciación por Source: El cliente puede usar el campo Source para distinguir si un cambio fue iniciado por un usuario local ("LocalApi") o llegó del polling externo ("InboundSync"). Esto permite, por ejemplo, no mostrar una notificación redundante al usuario que originó la acción.

CORS: Se configura via Realtime:AllowedOrigins en appsettings. Si no hay orígenes configurados, el CORS policy no se aplica. El hub requiere AllowCredentials() para el handshake de SignalR.

Fallback: Los Services aceptan ITodoRealtimeNotifier? como parámetro opcional. Si es null (ej: en tests), se usa NoOpTodoRealtimeNotifier que no hace nada.
